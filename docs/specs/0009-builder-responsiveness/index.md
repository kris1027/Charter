# 0009. Builder responsiveness: card level redraws, autosave on hide, and a live PDF preview rendered in a worker

**Date**: 2026-11-05
**Status**: Accepted

## Summary

Typing in the builder should never stutter, even on a long resume. Today a keystroke in one experience card redraws every card in that list. This spec makes each list follow only its length, so a keystroke redraws one field, and it saves the resume when the tab is hidden or closed, so you never lose the last 30 seconds. It also adds a live PDF preview beside the form on wide screens and in a sheet on phones. The PDF is built in a Web Worker (a background thread), so building it never blocks your typing, and pdf.js draws its pages.

## Requirements

**User stories**:

- As a job seeker with a long resume, I want typing in any field to feel instant, so the builder never lags behind me.
- As a job seeker, I want to see my resume in the chosen template while I type, so I do not have to jump to the Preview page to check how it looks.
- As a job seeker on a phone, I want to open the same preview on demand, so I can check the layout without leaving the form.
- As a job seeker, I want my typing saved when I close or leave the tab, so I never lose the last few edits.
- As a maintainer, I want tests that fail when a keystroke starts redrawing other cards again, so the gain cannot quietly erode.

**Acceptance criteria**:

- **AC-1**: With the long fixture loaded, typing one character into any field of experience card N renders no other experience card (`SortableCard`) and no other section card (`FormSectionCard`). The same holds for education and language cards. A Vitest render count test proves it for each of the three lists.
- **AC-2**: Experience, education and languages render their list from the list length alone. Add, remove, drag to reorder, reset and PDF import still show the right values in every field: the spec 0005 characterization tests in `builder-page.test.tsx` pass unchanged.
- **AC-3**: Autosave keeps its 30 second tick and its "skip when unchanged" check, and never writes on a keystroke. When the page fires `pagehide`, or `visibilitychange` with `document.visibilityState === 'hidden'`, it runs the same check and writes if anything changed since the last save. The same check also runs when the builder unmounts (leaving `/builder` through an in app link fires neither event). The flush only writes; it sets no React state when the builder is unmounting.
- **AC-4**: Validation stays form level (`validators: { onChange: resumeFormSchema }`). The before profile records how long the Zod check takes per keystroke. If it is over 2ms at 4x CPU slowdown, `/develop` records it and stops to route a validation change through `/architect`; this spec does not change validation.
- **AC-5**: A before and after Chrome DevTools Performance profile is recorded in [rationale.md](rationale.md#baseline): `pnpm preview`, the long fixture loaded, 4x CPU slowdown, 20 characters typed into experience 3's description, the preview panel open (after only). The after profile shows no main thread task over 50ms caused by a keystroke or a preview update. One extra after profile is taken with the React Compiler off, for information only.
- **AC-6**: At 1280px wide and up, with the panel open, a preview panel sits beside the form. It shows the current form values in the form's template (`templateId`) and the app language. It updates 700ms after the last change to the values, the template or the language. Store updates that leave the values unchanged (touched, blur, errors, submit state) start no wait. Values that fail validation (a bad email, a half typed date) still render as typed. When edits arrive while a render runs, only the newest values render next; anything older is never shown.
- **AC-7**: On `/builder`, `@react-pdf/renderer` runs only inside the preview Web Worker, never on the main thread. `/builder` first load stays within its `perf/budgets.json` budget (262 KB), `pnpm perf:size` passes with the `lazyEngines` list unchanged, and no builder module imports `renderResumePdf`, `template-pdf.tsx` or `template-viewer.tsx`.
- **AC-8**: The panel draws every page of the PDF with pdf.js onto canvases sized to the panel width, capped at 900 CSS px, at a pixel ratio of `min(devicePixelRatio, 2)`. A new render replaces the old pages only once all its pages are drawn, so the panel never flashes blank between updates, and the panel keeps its scroll position. A draw that a newer one has overtaken never replaces newer pages. A badge shows the page count ("2 pages"). The preview is never compacted, so the badge can read "2 pages" where `/preview` offers a one page fit; the panel header says "Full size, Preview can fit it to one page" when the count is over 1. Resizing the panel redraws the last good PDF at the new width.
- **AC-9**: The panel renders from the first values, even an empty form: the template's empty page shows before any field is filled. Until the first pages are drawn, the panel and sheet show one shared placeholder, "Preparing preview…".
- **AC-10**: On wide screens, a toggle in the builder toolbar shows or hides the panel. The choice is stored through `safeStorage` under `builderPreviewOpen` (`'1'` open, `'0'` hidden; missing means open) and applies on the next visit. While hidden, no render runs, and the form takes today's centered single column layout.
- **AC-11**: Below 1280px there is no side panel. A floating "Preview" button opens a full screen sheet that renders the current values at once (no 700ms wait) and shows the same pages, badge and notices. Escape or the close button closes it and returns focus to the floating button. No worker starts on a narrow screen until the sheet first opens.
- **AC-12**: When a render fails (react-pdf throws, or pdf.js cannot draw the result), the last good pages stay and a notice reads "Preview could not update". The next edit tries again, and a successful render removes the notice. A render with no answer within 30 seconds counts as failed. A draw cancelled because a newer one replaced it shows no notice.
- **AC-13**: When the worker cannot start (an `error` event before it reports ready, or no ready message within 20 seconds), or the worker reports an `error` or `messageerror` after ready, the panel or sheet shows "Live preview is unavailable here" with an Open preview button. That button runs the same submit as the Preview CV button (so it saves, and is disabled under the same rule: invalid or under 30% progress). The worker is not restarted during that visit. One exception: a `ready` that arrives after the 20 seconds (a slow but working load) recovers the panel and renders the current values. The form keeps working.
- **AC-14**: After one online visit to `/builder` that started the preview, the live preview works offline: the worker bundle and the PDF fonts are in the PWA precache. The worker bundle (each of its files) stays under the precache's 3 MB file limit (`maximumFileSizeToCacheInBytes`). Pass condition: in Chrome and Safari, DevTools offline after one online visit, reload `/builder`, type, and the panel updates.
- **AC-15**: The panel is an `aside` labelled "Live preview". Each page canvas has `role='img'` and a label "Resume preview, page 2 of 3". The toolbar toggle uses `aria-pressed`. The sheet traps focus and has a labelled close button. Notices use `role='status'`. Every new string has EN and PL keys (PL page counts use the `_one`, `_few`, `_many` and `_other` plural forms). With `prefers-reduced-motion`, the sheet opens without animation. The resume pages stay white in dark mode. The strings are the keys in the **Strings** table below.

## Decision

**Chosen option**: Option 2: fix the form in place, plus a live preview rendered in a Web Worker and drawn with pdf.js.

The list sections follow only their length, autosave also flushes on hide, validation stays as it is unless the profile shows otherwise, and a new live preview builds the PDF in a dedicated module worker and draws its pages with pdf.js on canvas, beside the form from 1280px and in a sheet below that.

**Implementation skills**: `tanstack-form` (`tanstack-skills/tanstack-skills`, `.agents/skills/tanstack-form/`) · `react-pdf` (`molefrog/skills`, `.agents/skills/react-pdf/`) · `vite` (`antfu/skills`, `.agents/skills/vite/`) · `vitest` (`antfu/skills`, `.agents/skills/vitest/`)

**States** (the live preview, per page visit):

`idle` (not active, no worker) → `starting` (worker created, waiting for ready; the "Preparing preview…" placeholder shows) → `ready` (pages shown) ⇄ `updating` (a render in flight; old pages stay) → back to `ready`. `starting` goes to `unavailable` on a worker `error` event or after 20 seconds; a late `ready` moves `unavailable` back to `ready`. An `error` or `messageerror` after ready also goes to `unavailable`, which is then final for the visit. A failed render (thrown, failed draw, or 30 seconds with no answer) sets `failed: true` and stays in `ready`; the next success clears it. Becoming inactive (panel hidden, sheet closed) stops new requests but keeps the worker alive for the visit; leaving `/builder` disposes it.

**Key invariants**:

- No builder module imports `@react-pdf/renderer`, `template-pdf.tsx`, `template-viewer.tsx` or `renderResumePdf`. The PDF reaches the builder only as bytes from the worker.
- At most one render runs in the worker, and at most one waits. The UI never shows a result older than one already shown.
- A keystroke causes no React render outside the edited field (and the progress and submit subscriptions when their selected values change).
- The resume pages are white in both themes. The preview never changes the saved resume.

**Security model**: no new data leaves the device. The worker is same origin (`worker-src 'self' blob:` already allows it) and needs no CSP change; react-pdf keeps using `wasm-unsafe-eval`. Fonts load from `/fonts/` as today.

**Configuration required**: none (no env vars). New storage key `builderPreviewOpen`.

## Consequences

**Positive**:

- A keystroke redraws one field instead of a whole list, and tests guard it.
- You see the real PDF while you type, built off the input thread, with no flash between updates.
- Closing the tab no longer loses up to 30 seconds of edits.
- The preview uses the same `TemplatePDF` as export, so it matches the full size download exactly (the compact one page export can differ; the panel says so).

**Negative / tradeoffs**:

- The worker bundle carries its own copy of react-pdf and the templates (several hundred KB), downloaded on first use of the preview on `/builder`. It is outside the page budgets, so `perf:size` does not watch it.
- Two PDF engines run on `/builder` while the panel is open (react-pdf in the worker, pdf.js for drawing), which costs memory and battery on wide screens; hiding the panel stops new renders.
- react-pdf inside a worker is less traveled than the main thread path; a react-pdf upgrade must be checked in the worker too.
- pdf.js still paints canvases on the main thread, in its own chunks of about 15ms; on very slow devices a paint can still be felt.
- The worker is not restarted after a crash in the same visit; a flaky network at first load means no live preview until a reload (a merely slow load still recovers).
- Worker bundle size is checked by hand in step 10, not by `perf:size`; a later growth past 3 MB would silently drop it from the precache.

**Neutral**:

- A new `src/features/pdf/live-preview/` area and a new `builder/live-preview/` folder; `AGENTS.md` (root storage keys, the pdf context file) needs the worker rule and the new key.
- `SortableList` changes its props, which every list section touches.
- The scope row 11 wording ("live preview smooth") now means this new panel.
