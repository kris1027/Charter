# 0006. Shared template model: one section registry for the PDFs, gallery cards from prebuilt PDF images

**Date**: 2026-11-04
**Status**: In Progress

## Summary

Today each of the three templates exists twice (an HTML copy for the gallery cards and a PDF copy for everything else), and the two copies have already drifted apart. This spec deletes the HTML copies. The gallery shows WebP images rendered from the real PDFs by a script, and a hash check in pre-commit fails when a template changes and the images were not regenerated. The three PDFs read one shared model (a plain TypeScript description of the sections, contacts, titles and formatted values) and map each section to their own small renderer, so the type checker refuses a new section until every template draws it. The first slice captures images of today's PDFs, so each later step proves with a pixel diff that the look did not change.

## Requirements

**User stories**:

- As the developer, I want a new resume section to be one entry in a shared list plus one small renderer per template, with the build failing until every template has it, so that I never forget a template or a gallery copy.
- As a job seeker browsing the gallery, I want each card to show exactly what the template exports, in my language, loading fast without jumping, so that I pick the template I'll really get.
- As a job seeker, I want my exported PDFs to look exactly as they do today and still import back, so that the refactor costs me nothing.

**Acceptance criteria**:

- **AC-1**: `pnpm templates:previews` (script `scripts/templates/build-previews.ts`, run with `node`, as the `perf:*` scripts are, so erasable syntax only) starts a Vite server with a minimal inline config: `configFile: false`, `appType: 'custom'`, `server: { middlewareMode: true }`, the `@` alias to `src`, `base` set to the absolute `public/` path with a trailing slash (see AC-11), and `oxc: { jsx: { runtime: 'automatic' } }` set explicitly. No React Compiler and no PWA plugin; the compiler only memoizes, so output is the same. It loads the app modules only through `ssrLoadModule`: `TemplatePDF`, `SAMPLE_RESUMES` and the fixtures. The script itself imports no `@/` path, since `tsconfig.node.json` can't resolve it. Rendering runs one document at a time: `renderToBuffer(<TemplatePDF … compactScale={0} />)`, wrapped as `new Uint8Array(buffer)` for pdfjs. Page 1 is rasterized with `pdfjs-dist/legacy/build/pdf.mjs` (no worker, `isEvalSupported: false`) through a canvas factory backed by `@napi-rs/canvas` (new dev dependency, loaded with a dynamic `import()` only in generate, baseline and diff modes) at 1190 × 1684 px (2× A4 at 595 × 842 pt). The pdf document is destroyed after each render. The script writes `src/features/templates/previews/<templateId>-<lang>.webp` (WebP quality 82) for every `TemplateId` × `AppLang` with `SAMPLE_RESUMES[id][lang]`. Six files, committed. The template list comes from `TEMPLATE_IDS`, so a fourth template gets images with no script change.
- **AC-2**: The same run writes `src/features/templates/previews/manifest.json`: `{ "inputsHash": "<sha256>", "files": ["developer-en.webp", …] }`. The hash covers these inputs, in sorted order and with text line endings normalized to `\n`: (a) every file Vite's SSR module graph loaded (from `server.moduleGraph`), with `?query` suffixes and virtual ids stripped, `node_modules` excluded, and only real files under `src/` kept; (b) `public/fonts/*.ttf`, as an explicit glob, since fonts are read at render time and are not modules; (c) the resolved versions of `@react-pdf/renderer`, `pdfjs-dist` and `@napi-rs/canvas`, read from their installed `package.json`; (d) the script files under `scripts/templates/`, which hold the raster size and WebP quality constants. Any edit to a shared input (for example `src/lib/utils.ts` or the sample data) also asks for a regeneration. That is accepted, because it is cheap. `pnpm templates:previews --check` loads the modules without rendering or loading the canvas library, computes the hash, and exits 1 with `Template previews are stale, run pnpm templates:previews` when the hash differs or a listed file is missing. `--check` is added to `pnpm pre-commit` after `prettier --write` and before `vite build`, and to the CI job next to `format:check`. It proves the images were regenerated after the last input change. It does not prove the committed bytes match a render on CI (WebP bytes may differ across machines), and that limit is accepted.
- **AC-3**: `pnpm templates:previews --baseline` renders every fixture (below) for every template, both languages and `compactScale` 0 and 1, every page, into the gitignored `.cache/template-baselines/`. For each render it saves `<templateId>-<lang>-<fixture>-<scale>-p<page>.png`, plus one `<templateId>-<lang>-<fixture>-<scale>.json` holding the extracted text lines (with the same line rebuilding `extractTextFromPDF` uses), the link annotation URLs in page order, and the PDF info fields (`Title`, `Author`, `Subject`, `Keywords`, `Creator`, `Language`). `--diff` renders again and compares, in plain code with no new dependency. It fails on any changed pixel (exact RGBA match, since baseline and diff run on one machine and the render is deterministic), on a page count change, or on any difference in the JSON. It prints each failing file, with its changed pixel count or the first differing JSON key. Fixtures live in `src/features/templates/fixtures/preview-fixtures.ts`, loaded through the Vite server: `sample` (the template's sample data); `full` (every contact including GitHub, an `https://` website and a LinkedIn URL with a trailing slash, a current job, a `NATIVE` language, multi line bullets, GDPR on with a company name); `minimal` (first name, last name and email only, every list empty, GDPR off); `edges` (empty `title`, education with only a degree and another with only a field, experience with no location, `current: true` with an `endDate` set, a website without a protocol, skills empty while every other list is filled); and `long` (enough experience and education to force a page break, so veterinary's `wrap={false}` blocks move).
- **AC-4**: The first slice runs `--baseline` against today's untouched templates, before any template file changes. After each template moves to the model, `--diff` against that baseline passes on the same machine. A failing diff blocks the step, and the step is not done until the diff passes.
- **AC-5**: `src/features/templates/model/` holds the shared model in plain TypeScript, with no `react`, `@react-pdf/renderer`, `i18next` or `@/i18n` import:
    - `section-ids.ts`: `SECTION_IDS = ['experience', 'education', 'skills', 'languages', 'interests'] as const` and `type SectionId`.
    - `template-strings.ts`: today's `pdf-translations.ts` moved here with the same strings, and with `PDFStrings` now exported (today it is a private `interface`). Every import of the old path is updated, and the old file is deleted.
    - `template-layouts.ts`: `TEMPLATE_LAYOUTS satisfies Record<TemplateId, TemplateLayout>`, where `TemplateLayout` is `{ sections: readonly SectionId[]; titles: Record<SectionId, (s: PDFStrings) => string>; contactRows: readonly (readonly ContactKind[])[]; dateStyle: 'long' | 'short'; websiteDisplay: 'raw' | 'short' }`. The values reproduce today exactly. Section order is the same five in the order above for all three. Titles: developer `// ${s.workExperience.toUpperCase()}`, `// EDUCATION`, `// TECH STACK`, `// LANGUAGES`, `// INTERESTS` (each built from its `PDFStrings` key, uppercased); default `professionalExperience`, `education`, `coreCompetencies`, `languages`, `interests`, each uppercased; veterinary `workExperience`, `education`, `skills`, `languages` as is and `specialInterests.toUpperCase()`. Contact rows: developer `[['website', 'github', 'linkedin'], ['location', 'email', 'phone']]`; default and veterinary `[['location', 'email', 'phone', 'linkedin', 'website']]` (no GitHub, as today). `dateStyle`: developer `long`, the others `short`. `websiteDisplay`: developer `short`, the others `raw`.
    - `resume-view.ts`: `buildResumeView(templateId, data, lang): ResumeView`, a pure function (details in _Feature design_).
    - `printed-title.ts`: `printedTitle(templateId, sectionId, lang)` returns `TEMPLATE_LAYOUTS[templateId].titles[sectionId](getPDFStrings(lang))`, the exact string the PDF prints.
- **AC-6**: Each PDF template (`developer-pdf.tsx`, `default-pdf.tsx`, `veterinary-pdf.tsx`) keeps its own styles, colors, fonts, header and look. It renders from `buildResumeView(...)` alone, never reading `data.experiences` or the other lists directly. Each declares `const renderers = { … } satisfies SectionRenderers`, where `SectionRenderers` is `{ [K in SectionId]: (section: ResumeView['sections'][K], ctx: RenderCtx) => ReactNode }`, so adding an id to `SECTION_IDS` fails `pnpm build` until all three templates render it. The body is `layout.sections.map((id) => view.sections[id].items.length > 0 ? <Fragment key={id}>{renderers[id](view.sections[id], ctx)}</Fragment> : null)`, with each section header printing `section.title`. Each renderer returns its whole block and owns its wrapper `View`, its `wrap` setting (as today; for example, veterinary experience wraps and its education does not) and any card styling (veterinary skills, languages and interests cards). The GDPR text comes from `view.gdpr` and stays last, where each template has it today. Contacts render by mapping `view.contactRows`. The icon comes from a `CONTACT_ICONS: Record<ContactKind, IconComponent>` map in `pdf-icons.tsx` (MapPin, Mail, Phone, Linkedin, Globe, Github, as today), and the icon color comes from `ctx.contactIconColor` (developer white, default `gray500`, veterinary `gray600`). An item with `href` renders as `Link`, one without (location) as `Text`, as today.
- **AC-7**: The helpers each template copies today live once, in `src/features/templates/pdf/pdf-scale.ts` (`lerp`) and in the model (`parseDescriptionLines` inside `resume-view.ts`). `src/features/templates/pdf/resume-document.tsx` exports `ResumeDocument`. It takes `templateId`, `data`, `view`, `lang`, `pageStyle` and `children`, and renders `Document` with today's values: `title` and `author` from `view.name` (`` `${first} ${last} - Resume` `` and `` `${first} ${last}` ``), `subject='Professional Resume'`, `keywords` as `view.sections.skills.items.join(', ')`, `creator={buildResumeMetadata(templateId, data)}` and `language={lang}`, plus one A4 `Page` with the template's page style. All three templates use it, so the embedded metadata (`v: 1`) is unchanged and a PDF exported after this change imports back with every field intact.
- **AC-8**: `pdf-parser.ts` reads every section header it looks for from `printedTitle(templateId, id, lang)` for both `en` and `pl`, in place of its literals, in `detectTemplate` and in the three `parse*Template` index lookups. It keeps the comparison style each lookup uses today: developer `includes` for all five; default equal to the line for all five; veterinary `includes` for work experience, education and interests, and equal to the line for skills and languages. It also keeps the extra variants it accepts today (`Professional Experience`, `Education`, `Core Competencies`, `Languages`, `Interests`, `Work Experience`, `Skills`, `EDUCATION`, `SKILLS`, `LANGUAGES`, `INTERESTS`) as a named `LEGACY_HEADERS` list, so an older PDF still imports. Detection: developer first (its `// ` work experience or tech stack title in either language), then default (its experience or core competencies title in either language), then veterinary (its interests title in either language), with developer as the fallback. Default moves ahead of veterinary because in Polish both print `ZAINTERESOWANIA` for interests, while default's `DOŚWIADCZENIE ZAWODOWE` and `KLUCZOWE KOMPETENCJE` are uppercase and only default prints them. In English the result is unchanged, because no default title is printed by veterinary. Every existing `pdf-parser.test.ts` case passes unchanged. New cases prove a Polish developer, default and veterinary export text each detects as its own template and has its experience section found.

## Decision

**Chosen option**: Option 1: Prebuilt PDF images for the gallery, plus a shared section registry with per template renderers.

The HTML templates are deleted. The gallery shows WebP renders of the real PDFs, kept current by an input hash check. The three PDF templates render from one plain model (`buildResumeView` plus `TEMPLATE_LAYOUTS`) through renderer maps the type checker holds complete.

**Implementation skills**: `react-pdf` (`molefrog/skills`, `.agents/skills/react-pdf/`) for `renderToBuffer`, `Document` metadata and styles · `vite` (`antfu/skills`, `.agents/skills/vite/`) for `createServer` with `ssrLoadModule` and the module graph · `vitest` (`antfu/skills`, `.agents/skills/vitest/`) for the model and parser tests.

## Feature design

**Data model sketch** (the view model, built fresh on every render, never stored):

| Type             | Fields                                                                                                                                                                                                                                                                                            |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ResumeView`     | `name: { first, last }`, `title: string` (`''` when empty), `contactRows: ContactItem[][]`, `sections: { experience: Section<ExperienceItem>; education: Section<EducationItem>; skills: Section<string>; languages: Section<LanguageItem>; interests: Section<string> }`, `gdpr: string \| null` |
| `Section<T>`     | `title: string` (from `printedTitle`), `items: T[]`                                                                                                                                                                                                                                               |
| `ContactItem`    | `kind: ContactKind` (`'location' \| 'email' \| 'phone' \| 'linkedin' \| 'website' \| 'github'`), `text: string`, `href: string \| null`                                                                                                                                                           |
| `ExperienceItem` | `position`, `company`, `location` (`''` when empty), `start: string`, `end: string`, `bullets: string[]`                                                                                                                                                                                          |
| `EducationItem`  | `degree`, `field`, `institution`, `startYear: string`, `endYear: string`, `description: string`                                                                                                                                                                                                   |
| `LanguageItem`   | `name: string`, `level: string`                                                                                                                                                                                                                                                                   |

`ContactItem` lists only filled fields. Rows that end up empty are dropped from `contactRows`. `ResumeView` holds strings only, so renderers never format anything. Items map one to one from `ResumeData` in the same order, with no trimming or filtering of entries (as today): skills from `skills[].name`, interests from `interests[].name`, languages from `languages[].language` and `.proficiency`, experience and education field by field. How a renderer joins values stays per template, as today. Default and veterinary join degree and field with the literal `' in '` (see Follow-up), and each template prints the experience location its own way. `RenderCtx<S>` is `{ lang: AppLang; compactScale: number; styles: S; contactIconColor: string }`, where `S` is `ReturnType<typeof createStyles>` of that template.

**Key invariants**:

- Every `TemplateId` has a layout, and every layout titles every `SectionId` (`satisfies Record<…>` enforces both).
- Every template's `renderers` covers every `SectionId` (`satisfies SectionRenderers`).
- A section whose list has length 0 renders nothing, header included, in every template. Entries with blank names still count, as today.
- The model imports no React, react-pdf or i18n code, so the parser and Node script can load it cheaply.
- The committed images and `manifest.json` match the current inputs (enforced by `--check`).
- Nothing outside `stored-resume.ts` touches storage (unchanged; the model reads no storage).
- The spec 0002 import rule holds: `model/` sits inside `templates`, `pdf` imports it (allowed), `resume` does not.

**Security model**: no change. Everything stays client only; the images are static public assets showing sample data, never user data.

**Configuration required**: none (no env vars). New dev dependency `@napi-rs/canvas`. New gitignore line `.cache/`. New script `templates:previews` in `package.json`. A `webp` runtime cache rule in `vite.config.ts`.

**Critical test scenarios**:

- Happy path: `buildResumeView('developer', sampleResumeData, 'en')` returns developer titles with the `// ` prefix, long dates, and two contact rows (website, GitHub, LinkedIn, then location, email, phone), verifies **AC-5**
- Contacts: default layout with GitHub filled shows no GitHub item; a website `https://x.dev/` is raw for default and short for developer; empty phone drops the item; a row with every field empty is dropped, verifies **AC-5**, **AC-6**
- Dates and levels: `current: true` gives `present` in EN and `Obecnie` in PL; `NATIVE` gives `Native` / `Ojczysty`; `B2` stays `B2`, verifies **AC-5**
- Bullets: `'• one\n\n- two\n  *three'` gives `['one', 'two', 'three']`, verifies **AC-7**
- GDPR: off gives `null`; on with `'  '` company gives the generic text; on with `ACME` names ACME, verifies **AC-5**, **AC-6**
- Titles: `printedTitle('veterinary', 'interests', 'pl')` is `ZAINTERESOWANIA`; `printedTitle('default', 'skills', 'en')` is `CORE COMPETENCIES`, verifies **AC-5**, **AC-8**
- Parser: every existing case passes; Polish developer, default and veterinary export texts each detect as their own template (default is not mistaken for veterinary through `ZAINTERESOWANIA`) and have their experience section found, verifies **AC-8**
- Look unchanged: `--diff` passes for all five fixtures, both languages, at scale 0 and 1, with zero changed pixels and identical text, links and info fields, verifies **AC-3**, **AC-4**, **AC-7**
- Staleness: editing a template's color without regenerating makes `--check` exit 1, verifies **AC-2**
- Gallery: rendering the gallery in PL shows images whose `alt` uses the PL key, with `width` and `height` set, verifies **AC-9**

## Build plan

Tracer Bullet: the first slice runs the whole pipeline (script, model, one template, gallery image) end to end. Each later slice moves one more template and keeps the app shippable.

Run `--baseline` on today's code and commit nothing from `.cache/`. The `pdf-fonts.ts` change is the only template side edit here, and it leaves browser output unchanged, satisfies AC-3, AC-4, AC-11.
2. **Model skeleton plus the default template, end to end.** Create `model/` (`section-ids`, `template-strings` moved from `pdf-translations`, `template-layouts`, `resume-view`, `printed-title`) with its tests, plus `pdf-scale.ts`, `resume-document.tsx` and `section-renderers.ts`. Move `default-pdf.tsx` onto them, then run `--diff`, satisfies AC-5, AC-6, AC-7, AC-13.
3. **Gallery images, end to end.** Generate the six images and `manifest.json`, add `--check` to `pre-commit` and CI, switch `TemplateCardPreview` to `<img>` with the new i18n key, and add the `webp` runtime cache rule. The developer and veterinary cards use their images too from here (the images come from today's PDFs, which are already the reference), so delete all of `html/` and the other two preview files in this step, satisfies AC-1, AC-2, AC-9, AC-10.
4. **Developer template on the model.** Move it, run `--diff`, then regenerate the previews. The regenerated images and `manifest.json` go in the same commit as the template change, or `--check` fails pre-commit, satisfies AC-4, AC-6.
5. **Veterinary template on the model.** Same as step 4, including the images and manifest in the same commit, satisfies AC-4, AC-6.
6. **Parser reads model titles.** Add `LEGACY_HEADERS`, the new detection order and the PL cases, satisfies AC-8.

## Migration plan

**Strategy**: strangler, one template at a time behind an unchanged `TemplatePDF` entry point.
**Phases**: as the build plan; each template switches in its own commit, guarded by `--diff`.
**Rollback**: revert the one template's commit. The model is additive until all three use it.
**Risks**: Vite SSR plus react-pdf in Node may need `ssr.noExternal` for `@react-pdf/*` if module resolution fails; that goes in the script's inline config only. pdfjs in Node needs the legacy build and no worker (`disableWorker` or the fake worker), again in the script only.

## Consequences

**Positive**:

- A new section is one `SECTION_IDS` entry, one view field, one title per layout and one renderer per template (three small spots, all forced by the compiler), down from six free form edits plus the parser.
- Gallery cards finally match the export, render in no time with fixed dimensions, and drop the HTML templates and their icons from `/templates`.
- Section headers live in one place for render and import, so renaming one cannot silently break import.
- A reusable pixel diff exists for any later template change (feature "Template visual refresh").

**Negative**:

- Binary images in git, regenerated on every template change (about 6 × 50 KB per change). The hash check forces regeneration, which adds a step to every template edit.
- A native dev dependency (`@napi-rs/canvas`). Prebuilt binaries cover macOS and Linux CI, but an unusual platform could fail to install it. It is dev only and never shipped.
- The gallery no longer reflects the user's chosen language until the image loads, and cards can't show anything dynamic (they never did).
- The pixel diff is only trustworthy on one machine, so the baseline is local and never committed.
- `--check` proves regeneration happened after the last input change, not that the committed bytes equal a CI render.
- Detection order changes (default before veterinary) to fix Polish; English detection is unchanged, but it is a parser behavior change.
- Templates now read a view model and can't reach raw `ResumeData`, so a template specific display tweak first needs a layout option or a view field.
