# PDF templates, export and import

## Overview

The three resume templates rendered with `@react-pdf/renderer`. They drive the live preview, the template detail page and the downloaded file. The import side (`pdfjs-dist`) reads an exported PDF back into the form, so render and parse are one round trip and change together.

## Conventions

- No `t()` or React context here: react-pdf renders outside the i18n provider. Section titles and the GDPR text come from `model/template-strings.ts`; add new strings there in both `en` and `pl`, keeping the wording in step with `cv.*` keys in the locale files.
- Dates come from `@/lib/date-format` with the template's `lang` prop, never `@/lib/date-utils`: that one imports `@/i18n/config` to default the language.
- Templates render from `buildResumeView(...)` only, never from `ResumeData` lists directly; the view holds formatted strings, so renderers format nothing.
- Every template imports `@/features/templates/pdf/pdf-fonts` and styles through `createStyles(compactScale)`, where `lerp(normal, min, t)` (`pdf-scale.ts`) shrinks sizes from 0 (normal) to 1 (most compact). New sizes should go through `lerp` so the one page fit keeps working.
- Colors are literal hex in a local `C` object; the page background stays white.
- `ResumeDocument` embeds `buildResumeMetadata(templateId, data)` in the PDF `creator` field (versioned payload `v: 1`). Import reads that first, so a shape change to `ResumeData` needs the payload handled (bump `v` or keep it compatible).
- A new section is a `SECTION_IDS` entry, a `ResumeView` field, a title per layout and a renderer per template; then run `pnpm templates:previews`.
- Any template change: run `pnpm templates:previews --baseline` before it and `--diff` after (zero changed pixels when the look should not change), then `pnpm templates:previews` and commit the images and `manifest.json` with the change, or `--check` fails pre-commit and CI.
- The text fallback in `src/features/pdf/import/` reads section headers through `printedTitle` (plus `LEGACY_HEADERS` for older English exports), so renaming a title updates render and import together. A printed layout change (line order, separators, columns) needs the matching `readers/<templateId>.ts` change; the round trip test (`*.pdf.test.tsx`, its own Vitest project in Node) fails until it reads back. A new loss goes into `expected-after-print.ts` with its reason.
- Import failures throw `PdfImportError` (`invalid`, `password`, `unrecognized`); the builder shows `dialogs.pdfError.<code>`, never `err.message`.
- `@react-pdf/renderer` is heavy and never in a page's first load (spec 0008): blobs go through `renderResumePdf` in `pdf-export.tsx` (dynamic import), and the gallery detail page's on screen PDF through `LazyGalleryPdfViewer` (over `gallery-pdf-viewer.tsx`, which uses `BlobProvider` so the page knows when the PDF has loaded, spec 0011). Never import it, `template-pdf.tsx` or `gallery-pdf-viewer.tsx` statically from page code; `pnpm perf:size` fails on a leak listed in `perf/budgets.json` `lazyEngines`.
- The builder's live preview and `/preview` render react-pdf only inside `src/features/pdf/live-preview/preview-worker.tsx`, reached through `createPreviewClient`, never on the page's main thread (spec 0009, spec 0013; the one exception is the `/preview` Download fallback through `exportToPDF`). The client has one waiting slot and one result callback with no request id, so a caller that needs each answer (the `/preview` fit search) keeps one request outstanding at a time. The worker needs `worker: { format: 'es' }` in `vite.config.ts`.

## Gotchas

- react-pdf lays out each JSX text child as its own run: `{a} - {b}` and `{a} -{' '}{b}` print the same text with glyphs shifted by a fraction of a pixel. Keep a split as it is when the look must not change.
- pdfjs prints letter spaced text (default's headers) with a space between letters and fills every gap between runs with a whitespace run: match headers with `headerText`, split columns and tags with `cells` (gaps measured between text runs, `CELL_GAP`).
- The pixel diff baseline in `.cache/` is only valid on the machine that made it; never commit it.
- `scripts/templates/build-previews.ts` runs under plain `node` (erasable TS only) and can't import `@/` paths: it loads app modules through Vite `ssrLoadModule`, but imports `react` and `@react-pdf/renderer` with a plain `import()`, since a bare package id through `ssrLoadModule` gets inlined and fails on CommonJS. Its Vite `base` is the absolute `public/` path, which is why `pdf-fonts.ts` skips `?v=` for a file system base.
- Gallery images are not precached; `vite.config.ts` serves them through a `CacheFirst` runtime rule (`template-previews`), so a gallery opened once works offline.
- react-pdf needs WebAssembly and blob frames: the CSP in both `vite.config.ts` and `vercel.json` allows `wasm-unsafe-eval` and `blob:`. Tightening either breaks preview and export in production only.
- `pnpm perf:size` does not watch the live preview worker (`assets/preview-worker-*.js`, about 1.2 MB in spec 0009). Any file over `maximumFileSizeToCacheInBytes` (3 MB, `vite.config.ts`) silently drops out of the PWA precache and the preview stops working offline, so check its size after a react-pdf upgrade or a template change, and check the upgrade in the worker too.
- `draw-pdf-pages.ts` opens PDFs with `disableFontFace: true`: registering each render's fonts in `document.fonts` would lay out the whole builder page again on every update. pdf.js takes ownership of the bytes it gets, so never reuse a buffer after `loadPdf`.
- Changing a font file requires bumping `v` in `pdf-fonts.ts`, or the PWA cache serves the old one. JetBrains Mono was dropped for Fira Code because of a fontkit incompatibility.
